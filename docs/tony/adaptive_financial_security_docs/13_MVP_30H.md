# 13 — MVP 30h

## Objetivo de demo

Demostrar una sola cosa:

> **Una cuenta puede mantenerse protegida ante una operación anómala aunque el usuario no pueda responder inmediatamente, sin bloquear todo de forma ciega.**

## No construir

- core bancario real;
- scoring ML entrenado;
- KYC;
- red interbancaria real;
- app completa;
- 20 tipos de fraude.

## Construir

### 1. Simulador de cuenta
- saldo;
- historial;
- beneficiarios;
- dispositivo;
- preferencias de protección.

### 2. Risk events
- nuevo beneficiario;
- monto anómalo;
- nuevo dispositivo;
- remote-access flag;
- user unreachable.

### 3. Policy engine

```text
low risk → allow
medium → adaptive challenge
high + reachable → challenge
high + unreachable → temporary hold
critical → block + human review
```

### 4. User modes
- available;
- unreachable;
- compromised device;
- accessible-alt-channel.

### 5. Evidence view
Mostrar por qué se tomó la decisión.

## Demo principal

### Escenario 1 — viajero sin señal

1. historial normal;
2. usuario entra en estado unreachable;
3. nuevo dispositivo intenta transferencia grande;
4. sistema detecta riesgo;
5. push no recibe respuesta;
6. no interpreta silencio como aprobación;
7. coloca hold;
8. usuario vuelve 48h después;
9. verifica por canal alternativo;
10. operación se cancela/libera.

### Escenario 2 — user authenticated but manipulated

1. dispositivo legítimo;
2. FaceID correcto;
3. nuevo beneficiario + transferencia fuera de patrón;
4. sistema activa scam-specific challenge;
5. pregunta si alguien está guiando operación;
6. cooldown / escalation.

### Escenario 3 — channel mismatch

1. challenge estándar falla;
2. sistema selecciona método alternativo configurado;
3. usuario completa verificación sin tercero obligatorio.

## Stack conceptual

Frontend → API → risk engine → policy engine → agent/orchestrator → mock bank data.

## Definition of Done

- URL pública;
- flujo reproducible;
- 3 escenarios;
- decisiones explicables;
- latency razonable;
- README claro;
- sin claims inventados.
